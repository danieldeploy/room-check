# Site-wide PT/EN translation

The portal uses two translation layers. They have different responsibilities and must not be mixed.

## 1. Static interface text

Static interface text includes headings, buttons, menu entries, placeholders, notices, validation messages and text created by JavaScript.

`src/I18n/SiteTranslations.php` is the shared catalogue for the whole website. Authenticated pages automatically load it through `SessionBar::render()`. The login page loads it directly. Legacy static strings discovered by the source audit live in `src/I18n/SiteTranslationsCoverage.php` and are merged into the same runtime catalogue.

For a new module, use the normal application shell and `SessionBar`. For new static strings, prefer declaring both languages together:

```php
require_once __DIR__ . '/src/I18n/SiteTranslations.php';
SiteTranslations::boot();

echo SiteTranslations::text('Guardar', 'Save');
```

For a formatted message:

```php
echo SiteTranslations::format(
    'Foram guardados {count} registos.',
    '{count} records were saved.',
    ['{count}' => (string) $count]
);
```

The browser translation runtime also supports audited `{value}` templates. This allows text created by JavaScript or API responses with variable values to be translated without translating the variable itself.

Existing Portuguese markup remains supported by the output translation layer, which translates visible DOM text and observes DOM changes. JSON/API payloads, script data, IDs and canonical database values are deliberately not rewritten.

JavaScript-generated visible text is covered by the DOM observer when its Portuguese source text is present in the shared catalogue. New JavaScript modules should keep user-visible text in the site catalogue and may call `window.translateAppText(text)` when an immediate translated string is needed.

Technical markup is deliberately excluded from automatic DOM translation. `code`, `pre`, `kbd`, `samp`, scripts, styles and textareas are not rewritten. A future module can also mark any technical subtree with `data-i18n-skip`.

## 2. User-authored persistent content

User-authored natural-language content must be stored in both languages. Do not put it in `SiteTranslations`.

Use paired columns, for example:

- `name` / `name_en`
- `description` / `description_en`
- `instructions` / `instructions_en`

When creating user text, use:

```php
$versions = $contentTranslator->versions($text, Translator::locale());
```

When editing an existing bilingual value, always pass the saved pair:

```php
$versions = $contentTranslator->versions(
    $text,
    Translator::locale(),
    $existingPt,
    $existingEn
);
```

That order is important: an unchanged saved value is reused before calling the provider. This prevents a multi-field form from retranslating unchanged content.

Genuinely new or changed text is sent directly to Google Cloud Translation Basic. The active interface language supplies the explicit source language (`pt-PT` or `en`), and the other language is the target. There is no local dictionary, spelling gate, language detector, manual vocabulary or unknown-word list.

The browser never calls a validation-only translation endpoint. Translation occurs only as part of a real persistence operation, including an existing field's real autosave.

A failed translation must never be stored as if it were the other language. `ContentTranslator` checks only that Google returned a successful, structurally valid, non-empty response and that protected quoted text/numbers can be restored. It does not judge vocabulary, grammar or the relative length of the translation. Persisted translations are reused and are not translated again on page view.

If the configured daily quota is reached, an authenticated save is normalized into a whitelisted operation and stored in `translation_pending_jobs`. The source text is a draft only: the authoritative PT/EN columns are unchanged until the worker obtains both versions. The worker verifies the queued state fingerprint under a database lock and applies the operation atomically. A later edit for the same target increments its generation and supersedes the older draft; unrelated provider failures have bounded retries and never create a false translation.

When reading persistent bilingual content, use `Translator::localized()` at the server/data boundary. Inputs, textareas, selects, JSON view-models and normal page text must all receive the active-language value rather than relying on DOM translation of the canonical PT value.

Names of people, usernames, email addresses, phone numbers, room numbers, dates, PINs, SIP values, My2N IDs, enum values, status keys, URLs, API keys, tokens and other machine identifiers are not translated, do not use `ContentTranslator::versions()`, and do not need paired `_en` columns.

## 3. Automatic source-code audits

`tests/static-i18n-audit.php` scans PHP and JavaScript source for Portuguese-looking static literals. It compares them with the shared PT/EN catalogue and fails CI when a new uncovered user-visible string is introduced.

`tests/persistent-i18n-boundaries.php` verifies that current persistent bilingual fields are localized from their PT/EN database pair at the data/view boundary while canonical machine identity remains unchanged.

`tests/bilingual-write-audit.php` recursively scans all application PHP, including future modules. It discovers PT/EN column pairs from `database.sql` and fails CI when user-facing code:

- writes only one side of a PT/EN pair;
- writes bilingual content without `ContentTranslator`;
- does not use `Translator::locale()`;
- bypasses `->versions(...)`;
- performs an UPDATE/upsert without a 4-argument `versions(text, locale, existingPt, existingEn)` path.

Only exact migration files are exempt. Ordinary new modules are included automatically and do not need to be added to an allowlist.

This means future modules must classify every new text value at development time:

- static human-readable UI text -> PT/EN catalogue;
- user-authored natural-language text -> paired PT/EN database columns + `ContentTranslator::versions()`;
- machine/technical value -> one canonical value, never translated.

## Rules for future modules

1. Render the shared `SessionBar` on authenticated HTML pages.
2. Use `SiteTranslations::text()` for new static UI strings when practical.
3. Add reusable/static Portuguese-to-English pairs to `SiteTranslations::catalog()` or the audited coverage catalogue.
4. Never translate IDs, API keys, enum values, usernames, device identifiers, PINs, SIP values or other machine values.
5. Store editable/user-authored natural-language content in paired PT/EN database columns.
6. Route every editable bilingual save through `ContentTranslator::versions()`; do not implement preview/validation translation endpoints.
7. On edits/updates, pass both saved language values to `versions()` so unchanged fields are reused before the provider call.
8. Do not add local linguistic gates, dictionaries, unknown-word checks or automatic language detection.
9. Use `Translator::localized()` to choose the saved language at display/edit time.
10. Do not translate JSON/API payloads globally; localize only user-visible content at the data/UI boundary.
11. Mark technical DOM subtrees with `data-i18n-skip` when needed.
12. Keep the Google key in the server environment or in the configured JSON secrets file outside `public_html`; never place it in browser code, translation storage or the repository.
13. Add both PT and EN cases to tests whenever a new module contains localized business content.
14. Do not bypass translation audits with broad exclusions; classify the value correctly instead.

The repository CI runs PHP syntax validation, JavaScript syntax validation, the application tests, `tests/i18n.php`, the persistent bilingual boundary audit, the recursive bilingual-write audit and the fail-closed static translation audit. A new translation path that bypasses these rules therefore blocks the pull request before deployment.

This structure allows future modules (including Bell/My2N extensions) to inherit the same language selection, unchanged-value reuse and technical translation safeguards without duplicating translation code.


## Transversal bilingual textarea contract

Editable user-authored item-list instruction textareas use the shared `data-bilingual-textarea` contract. The shared client keeps the last persisted value for Cancel edit and protects pending edits during navigation. Existing item instructions opt into a real blur autosave with `data-bilingual-autosave-action`. New-item textareas make no translation request on blur; they are translated and persisted only when the item-creation form is submitted. Technical/non-natural-language textareas must not opt in.
