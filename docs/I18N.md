# Site-wide PT/EN translation

The portal uses two translation layers. They have different responsibilities and must not be mixed.

## 1. Static interface text

Static interface text includes headings, buttons, menu entries, placeholders, notices, validation messages and text created by JavaScript.

`src/I18n/SiteTranslations.php` is the shared catalogue for the whole website. Authenticated pages automatically load it through `SessionBar::render()`. The login page loads it directly. Legacy static strings discovered by the source audit live in `src/I18n/SiteTranslationsCoverage.php` and are merged into the same runtime catalogue.

For a new module, use the normal application shell and `SessionBar`. For new static strings, prefer declaring both languages together:

```php
require_once __DIR__ . '/src/I18n/SiteTranslations.php';
SiteTranslations::boot();

echo SiteTranslations::text('Guardar', 'Save');
```

For a formatted message:

```php
echo SiteTranslations::format(
    'Foram guardados {count} registos.',
    '{count} records were saved.',
    ['{count}' => (string) $count]
);
```

The browser translation runtime also supports audited `{value}` templates. This allows text created by JavaScript or API responses with variable values to be translated without translating the variable itself.

Existing Portuguese markup remains supported by the output translation layer, which translates visible DOM text and observes DOM changes. JSON/API payloads, script data, IDs and canonical database values are deliberately not rewritten.

JavaScript-generated visible text is covered by the DOM observer when its Portuguese source text is present in the shared catalogue. New JavaScript modules should keep user-visible text in the site catalogue and may call `window.translateAppText(text)` when an immediate translated string is needed.

Technical markup is deliberately excluded from automatic DOM translation. `code`, `pre`, `kbd`, `samp`, scripts, styles and textareas are not rewritten. A future module can also mark any technical subtree with `data-i18n-skip`.

## 2. User-authored persistent content

User-authored natural-language content must be stored in both languages. Do not put it in `SiteTranslations`.

Use paired columns, for example:

- `name` / `name_en`
- `description` / `description_en`
- `instructions` / `instructions_en`

When saving user text, use `ContentTranslator::versions()` with the current locale. When reading it, use `Translator::localized()`.

Before translation or persistence, `ContentTranslator::versions()` runs the single server-side `LanguageGuard`. If the interface/input language is English and the submitted text is clearly Portuguese, or vice versa, the save is rejected before the translation provider is called. Ambiguous text, proper names, brands and neutral technical terms are allowed.

There is deliberately no duplicate browser language detector. The server is the only source of truth, so every normal form, API call and future client gets the same validation without trusting client-side JavaScript.

A failed translation must never be stored as if it were the other language. `ContentTranslator` validates provider/cache output, rejects obvious mixed-language responses, and never persists a rejected result. Persisted translations are reused and are not translated again on page view.

Names of people, usernames, email addresses, phone numbers, room numbers, dates, PINs, SIP values, My2N IDs, enum values, status keys, URLs, API keys, tokens and other machine identifiers are not translated, do not use `ContentTranslator::versions()`, and do not need paired `_en` columns.

## 3. Automatic source-code audits

`tests/static-i18n-audit.php` scans PHP and JavaScript source for Portuguese-looking static literals. It compares them with the shared PT/EN catalogue and fails CI when a new uncovered user-visible string is introduced.

`tests/persistent-i18n-boundaries.php` verifies that current persistent bilingual fields are localized from their PT/EN database pair at the data/view boundary while canonical machine identity remains unchanged.

The audits understand the distinction between human-readable content and machine values. Exact server-only exceptions are kept deliberately small; adding an entire file or module as a blanket exception is not allowed.

This means future modules must classify every new text value at development time:

- static human-readable UI text -> PT/EN catalogue;
- user-authored natural-language text -> paired PT/EN database columns + `ContentTranslator::versions()`;
- machine/technical value -> one canonical value, never translated.

## Rules for future modules

1. Render the shared `SessionBar` on authenticated HTML pages.
2. Use `SiteTranslations::text()` for new static UI strings when practical.
3. Add reusable/static Portuguese-to-English pairs to `SiteTranslations::catalog()` or the audited coverage catalogue.
4. Never translate IDs, API keys, enum values, usernames, device identifiers, PINs, SIP values or other machine values.
5. Store editable/user-authored natural-language content in paired PT/EN database columns.
6. Route every editable bilingual save through `ContentTranslator::versions()`; do not implement separate page-specific language validation.
7. Let the central server-side `LanguageGuard` reject only high-confidence source-language mismatches before translation/persistence.
8. Use `Translator::localized()` to choose the saved language at display/edit time.
9. Do not translate JSON/API payloads globally; localize only user-visible content at the data/UI boundary.
10. Mark technical DOM subtrees with `data-i18n-skip` when needed.
11. Keep secrets and credentials outside translation storage and outside the repository.
12. Add both PT and EN cases to tests whenever a new module contains localized business content.
13. Do not bypass translation audits with broad exclusions; classify the value correctly instead.

The repository CI runs PHP syntax validation, JavaScript syntax validation, the application tests, `tests/i18n.php`, the persistent bilingual boundary audit and the fail-closed static translation audit. A new translation path that bypasses these rules therefore blocks the pull request before deployment.

This structure allows future modules (including Bell/My2N extensions) to inherit the same language selection, input-language validation and translation safeguards without duplicating translation code.
