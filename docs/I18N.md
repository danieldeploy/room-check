# Site-wide PT/EN translation

The portal uses two translation layers. They have different responsibilities and must not be mixed.

## 1. Static interface text

Static interface text includes headings, buttons, menu entries, placeholders, notices, validation messages and text created by JavaScript.

`src/I18n/SiteTranslations.php` is the shared catalogue for the whole website. Authenticated pages automatically load it through `SessionBar::render()`. The login page loads it directly.

For a new module, use the normal application shell and `SessionBar`. For new static strings, prefer declaring both languages together:

```php
require_once __DIR__ . '/src/I18n/SiteTranslations.php';
SiteTranslations::boot();

echo SiteTranslations::text('Guardar', 'Save');
```

For a formatted message:

```php
echo SiteTranslations::format(
    'Foram guardados {count} registos.',
    '{count} records were saved.',
    ['{count}' => (string) $count]
);
```

Existing Portuguese markup remains supported by the output translation layer, which translates visible DOM text and observes DOM changes. JSON/API payloads, script data, IDs and canonical database values are deliberately not rewritten.

JavaScript-generated visible text is covered by the DOM observer when its Portuguese source text is present in the shared catalogue. New JavaScript modules should keep user-visible text in the site catalogue and may call `window.translateAppText(text)` when an immediate translated string is needed.

## 2. User-authored persistent content

User-authored content must be stored in both languages. Do not put it in `SiteTranslations`.

Use paired columns, for example:

- `name` / `name_en`
- `description` / `description_en`
- `instructions` / `instructions_en`

When saving user text, use `ContentTranslator::versions()` with the current locale. When reading it, use `Translator::localized()`.

A failed translation must never be stored as if it were the other language. `ContentTranslator` leaves the missing target language empty (PT source) or rejects the save when an English edit cannot obtain the required Portuguese canonical counterpart. Persisted translations are reused and are not translated again on page view.

## Rules for future modules

1. Render the shared `SessionBar` on authenticated HTML pages.
2. Use `SiteTranslations::text()` for new static UI strings when practical.
3. Add reusable/static Portuguese-to-English pairs to `SiteTranslations::catalog()`.
4. Never translate IDs, API keys, enum values, usernames, device identifiers or other machine values.
5. Store editable/user-authored language content in paired PT/EN database columns.
6. Use `ContentTranslator::versions()` only when saving content, not when displaying it.
7. Use `Translator::localized()` to choose the saved language at display time.
8. Do not translate JSON/API payloads globally; localize only user-visible messages at the UI boundary.
9. Keep secrets and credentials outside translation storage and outside the repository.
10. Add both PT and EN cases to tests whenever a new module contains localized business content.

The repository CI runs `tests/i18n.php` in addition to the existing PHP and JavaScript validation, so the shared catalogue, HTML-only translation boundary and dynamic-DOM translation hook remain covered by regression tests.

This structure allows future modules (including Bell/My2N extensions) to inherit the same language selection and UI translation mechanism without duplicating translation code.
